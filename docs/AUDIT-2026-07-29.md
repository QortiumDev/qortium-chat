# Delta audit — 2026-07-29

Targeted multi-agent review of the four user-reported problems in Qortium Chat
v1.4.8 (`867e5df`): jumpy scrolling, cramped mobile view, public-network /
gateway read-only support, and avatar breakage. This is a **delta** audit on top
of [AUDIT-2026-07-01.md](AUDIT-2026-07-01.md) — it covers the five post-audit
PRs (#50, #51, #54, #56, #57) and the four symptom tracks; unchanged known
items from the July audit are not re-reported.

**Reviewed against:** qortium-chat `867e5df` (v1.4.8) · qortium-home 1.6.1
(`a22a7ec`) · qortium-core 1.6.1 (live Previewnet node `qortium-1.6.1-5f4fc2c`).

**Method:** native live repro against the running Previewnet node, then a
15-agent workflow — 7 review dimensions (scroll-rendering, avatar-delta,
regression-sweep, mobile-ux, gateway ×2 dual-model, new-user-ux) split across
Claude (Sonnet) and Codex (`gpt-5.6-terra`, `gpt-5.3-codex-spark`) per the
usage balancer, every high/medium finding adversarially verified by a
cross-model skeptic (Claude findings checked by Codex and vice versa), a
completeness-critic pass, one dimension re-run after a structured-output
failure, and native follow-ups closing the critic's gaps. All agents read-only.
Line numbers reference the commits above.

Severity = user impact. Verdicts: **CONFIRMED** (skeptic reproduced the
evidence), **REFUTED** (skeptic disproved it — kept here for the record),
unverified lows carry the reviewer's confidence only.

## 1. Scrolling (why it "jumps a bunch") — 4 confirmed, 1 low

The jumpiness is compounded, not singular. Ranked by contribution:

### 1.1 [High · CONFIRMED] Status lines steal the feed's `1fr` grid row — `src/styles.css:1455`
`.chat-pane` declares exactly three rows (`auto minmax(0,1fr) auto`), but
`App.tsx:5304-5328` renders up to ~8 conditional in-flow status/error nodes
between header and feed. Whichever appears first takes the `1fr` track; the
feed drops to an implicit auto-sized row and the composer to a fourth —
the feed becomes content-sized (unbounded `clientHeight`), which both cramps
the pane and invalidates every scroll computation. **Fix:** wrap notices +
feed in one `.chat-pane__content` grid item (itself `auto minmax(0,1fr)`,
`min-height:0`) so the feed always owns the remainder.

### 1.2 [High · CONFIRMED] 56px estimated row heights make scroll geometry a lie — `src/styles.css:1949`
Every `.message` has `content-visibility:auto; contain-intrinsic-size: auto 56px`.
Rows never yet rendered report 56px; real rows run 60–400px. `scrollHeight`
therefore mutates continuously while scrolling up through history, and the
one-shot prepend restore (`MessageList.tsx:1318-1342`,
`scrollTop = scrollHeight - anchor.scrollHeight + anchor.scrollTop`) plus
`scrollToBottom`'s math read it mid-churn. This is the classic "jumps a bunch
while scrolling up" signature. **Fix:** drop `content-visibility` from message
rows (accepting more layout work on very long histories), and replace the
height-delta prepend anchor with element anchoring — top-visible message key +
pixel offset through the existing bounded settle routine
(`scrollToAnchor`, `MessageList.tsx:973`).

### 1.3 [Medium · CONFIRMED] 15s DM/closed-group poll invalidates the feed unconditionally — `src/App.tsx:2108`
`loadMessages(..., {quiet:true})` fires every 15s (`App.tsx:4533-4538`) and
always commits a fresh array; the `messages`-dependent layout effect
(`MessageList.tsx:1272`) then re-runs `pinToBottom()` even when nothing
changed. **Fix:** bail out of the commit when a stable comparison (identity +
mutable edit/decrypt fields) finds no change; test no-op / edit / delete /
new-message cases.

### 1.4 [Medium · CONFIRMED] Image previews reserve no height; each load re-pins — `src/MessageList.tsx:148`
Preview `<img>` has no width/height/aspect-ratio (`styles.css:2591` caps at
320px), so each preview pops from one text line to up to 320px, and every load
fires `onLoadCapture → pinToBottom()` (`MessageList.tsx:1496-1503`) — N
previews = N visible snaps. **Fix:** decode natural dimensions into preview
metadata before render and emit width/height (no generic fixed ratio).

### 1.5 [Low · likely] Settle loop ignores scrollbar drags — `src/MessageList.tsx:911`
`scrollToBottom` re-writes `scrollTop` per frame (up to 360 frames ≈ 6s);
wheel/touch/key cancel it but a native scrollbar drag is classified as
programmatic (`MessageList.tsx:1514`) and gets fought. **Fix:** pointer
interaction with the list cancels the settle rAF and clears stick intent.

Also noted: all repositions are instant `scrollTop` teleports (no smooth
variants anywhere) — acceptable once 1.1–1.4 stop the involuntary movement,
but the jump-to-unread / down-arrow affordances would read better with a
`behavior:'smooth'` option gated on `prefers-reduced-motion`.

**Open cross-check (critic):** #50 edit/delete and #51 routing also mutate the
message array — verify during the fix that those paths don't independently
trigger the same re-pin (same mechanism as 1.3).

## 2. Avatars — 2 high + 2 medium confirmed, 1 refuted, 1 low

Live context (verified natively against the running node): **no pointer
avatars exist on Previewnet yet** — every `/addresses/{addr}/avatar/info`
probe 404s, so all real traffic takes the LEGACY branch
(`THUMBNAIL/{name}/avatar`, then `qortal_avatar`), which works end-to-end:
octet-stream + magic-byte sniffing resolves correctly, and gzip responses drop
`Content-Length` so the byte-length fallback engages. If avatars looked broken
on Android before 1.6.1, the likely cause was the secure-proxy bridge outage
fixed by home#230 — re-verify on-device before chasing chat-side causes.

### 2.1 [High · CONFIRMED] POINTER avatars silently dropped on any Content-Length mismatch — three host bridges + chat
Chat's `parseAccountAvatar` (`src/avatarProfiles.ts:102-116`) requires
`contentLength === bytes.byteLength` exactly, else the avatar is discarded
with no log. All **three** host bridges prefer the HTTP header over measured
bytes on the POINTER path: `qortium-home/electron/qdn.ts:6498`,
`qortium-home/src/platform.ts:5176`, and Core's read-only gateway bridge
`qortium-core/src/main/resources/q-apps/q-apps.js:1675`. Any transport that
decompresses or re-frames while a stale header survives (proxies, future
encodings) silently kills every pointer avatar. Latent today only because the
POINTER path is unexercised on-chain. **Fix (host side, all three):** return
measured byte length as `contentLength`; use the header only for the oversize
preflight. **Fix (chat side, defense):** treat `contentLength` as advisory —
validate bytes against `maxBytes` and drop the strict equality.

### 2.2 [High · CONFIRMED] Chat 1.4.8 shows no avatars at all on older Home (1.5.x/1.6.0) — `src/avatarProfiles.ts:129`
PR #56 removed the legacy `GET_QDN_RESOURCE_PROPERTIES`/`FETCH_QDN_RESOURCE`
fallback; when the host doesn't advertise `FETCH_ACCOUNT_AVATAR`, chat
returns `unavailable` before fetching anything. Auto-updated QDN app + older
Home = every avatar a letter placeholder. **Fix:** bounded legacy
`THUMBNAIL/{name}/avatar` fallback when the new action is absent but generic
resource actions exist; keep the new action preferred.

### 2.3 [Medium · CONFIRMED] PENDING retry loop has no attempt budget — `src/App.tsx:688-712`
A resource that stays HTTP 202 (unfetchable QDN data) retries forever at
1–30s intervals per address; a 50-sender group can sustain hundreds of bridge
calls/minute indefinitely. **Fix:** cap per request key (e.g. 10 attempts or
5 minutes), commit name-only profile, re-arm on chat/address refresh.

### 2.4 [Medium · CONFIRMED] Avatar fetch per rendered address, unbounded concurrency — `src/App.tsx:769-773`
#56 also dropped the `hasAvatar` gate: every distinct sender in
`combinedMessages` (the whole paginated history, not the viewport) gets a
bridge round-trip. **Fix:** concurrency cap (~6) + viewport/recency-aware
prioritization; keep the address-keyed cache.

### 2.5 [Medium · REFUTED] "Android skips the byte-cap check" — `src/platform.ts:5176`
Skeptic disproved: the cap is enforced on every path (`:5177`); only the
check *ordering* differs from desktop. No fix needed beyond 2.1.

### 2.6 [Low · likely] No `<img onError>` fallback — `src/accountDisplay.tsx:85`
A revoked-but-rendered blob URL or browser-undecodable image shows a broken
image instead of the letter fallback; Android also returns raw `response.data`
instead of re-encoding normalized bytes. **Fix:** `onError` → revoke + letter
fallback; normalize base64 on the Android bridge.

## 3. Gateway / read-only (dual-model dimension) — the premise was wrong, the gap is narrower and different

**Headline correction to the scouting brief:** Core 1.6.1 already ships a full
read-only `qdnRequest` bridge — `HTMLParser.java:73-75` unconditionally
injects `/apps/q-apps.js` into every served/rendered page, installing
`window.qdnRequest` with same-origin fetches, a validated read-action
allowlist (including `FETCH_ACCOUNT_AVATAR` with the LEGACY path),
`WHICH_UI = 'QORTIUM_GATEWAY'` and `IS_USING_PUBLIC_NODE = true`. Chat's reads
already route through `qdnRequest()`/`FETCH_NODE_API`, so group lists,
messages, members, names and legacy avatars **already work read-only** on a
node-served page today. Both independent reviewers converged on the same real
defects:

### 3.1 [High · CONFIRMED ×2] Chat misclassifies Core's read-only bridge as Home — `src/qdnRequest.ts:138`
`hasHomeBridge()` is `typeof window.qdnRequest === 'function'`; a gateway
visitor therefore gets `isHomeBridge = true`, Home-insider copy, and a
"connect account" affordance whose `GET_SELECTED_ACCOUNT` the bridge always
rejects (`q-apps.js:2199-2266` registers no such action) — a dead button on
the single worst first-run path (anonymous public-node visitor). The
`WHICH_UI` signal Core built for exactly this is fetched into
`BridgeState.ui` and never consulted. **Fix:** classify transport from
`WHICH_UI` (`'home' | 'gateway' | 'browser-dev'`), show an explicit "public
read-only view" state, never offer account actions on gateway. Feature gating
itself is already correct (driven by `hasAction` against the honest
`SHOW_ACTIONS` list).

### 3.2 [Medium] Gateway WebSockets can't work; chat retries them anyway — `src/App.tsx:4582`
`GatewayService` registers only the REST servlet; chat WebSockets exist only
on `ApiService`. Open groups on a gateway page burn a reconnect-backoff loop
before each REST fallback. **Fix:** on the gateway transport, skip WS and use
the existing 15s poll branch directly.

### 3.3 [Medium] Origin-wide localStorage on shared gateway origins — `src/chatStorage.ts:36`
On a gateway, co-hosted QDN apps share the origin; chat persists
account-address-keyed watermarks/bookmarks readable by any of them (July
audit's open question, now concrete). **Fix:** memory-only state on the
gateway transport. True isolation needs per-resource origins (Core-side,
out of scope).

### 3.4 [REFUTED for current stack] "No same-origin fallback for gateway pages" — `src/qdnRequest.ts:88`
Refuted because injection is unconditional on current Core. The
localhost-only `fallbackQdnRequest` matters only for **older Core** nodes and
plain-browser dev — acceptable to leave, worth a one-line doc note.

Core-side notes (analysis only, filed for awareness): `q-apps.js` shares bug
2.1; `IS_USING_PUBLIC_NODE` is hardcoded `true` even for an operator browsing
their own node's `/render` (over-restrictive, conservative direction);
read-only `GET_QDN_RESOURCE_URL` hardcodes `/render/...` instead of the
`_qdnContext`-aware branching its sibling `buildResourceUrl` uses.

## 4. Mobile UX (cross-repo) — 3 high, 3 medium, 1 low

Scout corrections (verified on 1.6.1): the top bar is a **2-row** grid (tab
strip + address/account/status), not 3 — the bookmark toolbar is opt-in and
default-hidden (`bookmarks.ts:79`). Real chrome: ~104–112px baseline,
~130–160px on notched devices, plus the viewer status handle. None of it
collapsible.

### Home-side (ranked by reclaimed pixels vs effort)
- **4.1 [High] `android:windowSoftInputMode="adjustResize"`** —
  `AndroidManifest.xml:14` has no soft-input mode, no `@capacitor/keyboard`,
  no `visualViewport` handling anywhere. One manifest attribute makes the
  WebView resize under the keyboard so chat's existing dvh pairs actually
  reflow. Biggest win per line of change; `@capacitor/keyboard` only as a
  follow-up if needed.
- **4.2 [High] Auto-collapse the top bar while an app is open** —
  `styles.css:2437` + `TopBar.tsx:1960/2439`; mirror the existing
  `statusHidden` pattern (`QdnViewer.tsx:4389-4425`) with a
  `.top-bar--collapsed` state (slim reveal strip), wired in `App.tsx:4126`.
  Reclaims ~80–100px in-app.
- **4.3 [High] Stop forcing the status handle to 34px** — the collapsed
  handle is 16px but `--with-badge` (any app with a manifest version — i.e.
  all real apps) bumps it to 34px (`styles.css:4459-4463`) and it re-expands
  on every in-app navigation (`QdnViewer.tsx:4400-4403`). Render the badge
  inline in the 16px handle.
- **4.4 [Medium] `GET_HOST_INFO` platform signal** — add additive
  `platform: 'android'|'ios'|'desktop'` to **both** bridge impls
  (`src/platform.ts:267-274` + `electron/qdn.ts:9309-9317`, known drift
  hazard) so apps can adapt density. Protocol change, additive; app-half
  (tolerant consumption) ships first per convention. Chat currently never
  calls `GET_HOST_INFO` at all.

### Chat-side
- **4.5 [Medium] `.composer textarea { max-height: 30vh }` unpaired** —
  `styles.css:3081`; add `30dvh` companion (pairing convention already used at
  555-556, 614, 3403-3404).
- **4.6 [Medium] Lightbox `calc(100vh - 96px)` unpaired** — `styles.css:2793`;
  same one-line pairing.
- **4.7 [Low · speculative] ≤600px density pass** — only container padding
  shrinks on mobile; message padding/gap/header/composer keep desktop values
  (`styles.css:1793/1943/1473/3032`). Compact overrides in the existing
  ≤600px block reclaim ~20-30px of feed. Verify visually before shipping.

**Open cross-check (critic):** keyboard show/hide resize vs the scroll settle
loop and anchor math (§1) — exercise together on-device once 4.1 lands.

## 5. Regression sweep (#50/#51/#54/#57) — 2 medium, 3 low

- **5.1 [Medium · CONFIRMED] #50 removed the edit-history UI** —
  `MessageList.tsx:1566`: the diff deleted `openHistories`/`toggleHistory` and
  the revision list; only the "edited" flag remains. If intentional, remove
  the dead strings/paths; if not, restore the affordance. *(Needs an owner
  call: regression or accepted simplification?)*
- **5.2 [Medium · CONFIRMED] Invalid host-pushed deep links die silently** —
  `App.tsx:3489-3507`: `historyMode:'push'` failures in an active session exit
  with no state change and no feedback. Fix: keep current chat, clear the
  stale route via `writeChatRoute({}, 'replace')`, show a non-blocking
  "conversation unavailable" notice.
- **5.3 [Low] Non-initial route resolution can force-jump to the first group**
  (`App.tsx:3523-3528`) even when a chat is already selected.
- **5.4 [Low] Machine-message filter can hide freeform human JSON**
  (`chatText.ts:71-89`: any `{"app": "...", <object sibling>}` without
  `message`). Consider a stricter marker. Also (critic): a deep link
  targeting a filtered message reproduces 5.2's silent-failure symptom.
- **5.5 [Low · speculative] Clipboard picks `files[0]` unconditionally**
  (`attachments.ts:47-64`) — revisit alongside Android share-sheet payloads
  (multi-file is common there; never cross-checked).

Dependency bumps (#52/#58): no behavioral API changes found; i18n parity test
coverage intact.

## 6. New-user UX — 2 high (1 refuted), 3 medium/low confirmed

- **6.1 [High · REFUTED as stated, real as UX]** "Nothing auto-selects on
  first run" — auto-selection *does* exist (`App.tsx:1823-1846`, 3482-3520),
  but it settles async, so first paint shows the contradictory
  "Select a chat" header + "No recent messages" body with a disabled,
  unexplained composer. Fix the flash: a real empty-state component with a CTA
  ("start with General Chat") instead of falling through to `MessageList`.
- **6.2 [High · CONFIRMED] Zero onboarding copy in the whole catalog** —
  no string explains General Chat is the public room, that group posts can
  need approval, or QDN publish delay. One dismissible line above the group
  list + a sentence in the approval notice covers it; no bridge changes.
- **6.3 [Medium · CONFIRMED] Disabled composer never says why** —
  `App.tsx:5444-5464`: no-chat-selected case has no notice and no `title`
  (the existing notice branches require `selectedChat`). Reuse the
  `composer--notice` pattern.
- **6.4 [Medium · CONFIRMED] Unavailability reasons are hover-only tooltips**
  — `App.tsx:1684-1748` labels feed `title=` on Send/Join/Leave/Direct —
  invisible on touch, chat's primary new-user surface. Surface inline in the
  narrow layout for the top controls.
- **6.5/6.6 [Low] `id:{groupId}` in every group row** (`chatLists.tsx:79`) is
  developer noise; General Chat's empty state should invite a first message
  instead of the generic "No recent messages" (`MessageList.tsx:1477`,
  `isGeneralChatGroup` helper already exists).

Compounded worst case (critic): the anonymous gateway visitor hits 6.1 + 6.3 +
3.1's dead connect button simultaneously — the gateway classification fix
(3.1) should land together with the read-only empty-state copy.
