## 1. Executive summary

The app remains fundamentally healthy: all 2026-06-22 audit fixes that were re-checked are intact (quiet-poll guard for messages/active-chats, inclusive `+1` history paging, paged approval tally, `RESOLVE_IDENTITIES` batching, Classic AA contrast, focus traps/outlines), the new **Modern uiStyle** layer is a clean CSS-only implementation whose bridge contract matches `qortium-home` field-for-field, tests and typecheck are green, and there are **no high-severity or data-loss defects**.

The 14 confirmed mediums cluster into five themes:

1. **Stale-async and quiet-poll gaps** — the request-guard pattern that `loadPendingApprovals` already implements was never applied to the message loaders, so a slow response can paint one chat's transcript (including private DMs) into another chat's pane; five background loaders still clobber the UI with transient errors (one wipes its data); a failed chat load shows the previous chat's transcript under the new chat's header; and the shared composer draft (including armed edit drafts) can be sent into the wrong chat.
2. **One incompletely-landed prior fix** — prior-audit priority #2 ("memoize the tree") shipped `React.memo` + the shared clock but never the recommended `useCallback`s, so the memo boundaries never bail; there is zero `useCallback` in `App.tsx`.
3. **Mobile CSS cluster** — at ≤600px the reply/edit banner collapses (Cancel goes full-width, label invisible); attachment-bearing messages clip their Reply/React/Edit buttons off the bubble on narrow screens; the coarse-pointer 44px pass missed the primary per-message touch controls.
4. **Modern dark contrast** — Modern dark's muted/faint token (#6f7a8c) computes to ~3.79:1 on message surfaces, below the AA 4.5:1 bar Classic was explicitly fixed to (timestamps + always-visible action buttons at 11px).
5. **Efficiency debt added since June 22** — an N+1 sweep fetches 100 messages per listed group every 30s just for a sidebar timestamp; scroll events do unthrottled synchronous localStorage writes; `emoji-picker-react` (~300 KB, a third of the JS chunk) is statically bundled though it only mounts on demand; plus a dead feature: `/blocks/height` is parsed as a string in both modes, so the approval-window ETA has never worked and windows are mislabeled "eligible now".

Feature-wise the biggest user-facing gap is **no new-message notification surface at all** (no OS notification, sound, or title badge — and polling pauses when hidden), followed by the known-deferred outbound-attachment path.

**Health:** strong. Every interval/WebSocket/rAF has matching cleanup + reconnect; watermark/divider/scroll logic is carefully reasoned; the Modern uiStyle path is CSS-only with normalizers verified against `qortium-home`'s `QdnViewer`/`qdn.ts` contract, with new Vitest coverage. ### 2.1 [Medium · new · CONFIRMED] Stale message loads commit into the currently selected chat (cross-chat transcript contamination) — `src/App.tsx:1468`
`loadMessages` commits `setMessagesChatKey(chatKey); setMessages({phase:'ready',…})` unconditionally; the same hole exists in `loadOlderMessages` (:1561), the post-send quiet refresh (:2036), the WS REST-fallback (:3056), and key-recovery reload (:1655). The chat-switch cleanup clears timers/sockets but can't cancel in-flight promises (bridge reads can be multi-second), so a stale chat-A response resolving after switching to chat B paints A's messages — possibly private DMs — into B's pane; on open-group WS chats subsequent frames **merge into** the stale value (:3033-3037) so it persists. `loadPendingApprovals` (:1801-1848) already implements the exact request-id + selection-ref guard needed. *(The efficiency dimension independently found the same defect; deduplicated here. Skeptic downgraded high→medium: display-only, same-account, direct/closed chats self-heal within 15s.)*
**Fix:** request token or `selectedChatKeyRef` comparison before every commit, mirroring the approvals guard.

### 2.2 [Low · new · CONFIRMED] Account switch baselines the new account's direct watermarks from the old account's chats and persists them — `src/App.tsx:2460`
During a `SELECTED_ACCOUNT_CHANGED` switch, `activeChats` still holds the old account's conversations while the watermark maps have already reset, so old-account addresses/timestamps are folded into the new account's `lastReadByAddress` and persisted (`writeReadWatermarks` :2603) after the one-shot skip ref is consumed. Skeptic verified the full mechanism but downgraded medium→low: realistic symptom is a spurious unread badge plus stale addresses persisted under the wrong account key, and Home's pinned-account model makes mid-session switches rare. **Fix:** clear `activeChats` in the same account-change effect, or tag the activity snapshot with its account.

- **Unthrottled scroll-bookmark localStorage writes** — see §7.3.

## 3. Correctness — API/bridge (1 confirmed, 5 low)

**Health:** sound. All prior-audit fixes intact and verified against the working tree; response shapes spot-verified against live Previewnet Core; Modern `uiStyle` signal matches Home's contract. No regressions.

### 3.1 [Medium · new · CONFIRMED] Block height parsed as a string in both modes — approval-window ETA permanently dead, window state mislabeled — `src/coreApi.ts:401`
Core serves `/blocks/height` as `text/plain` (verified live: bare digits). Both the fallback parser (`qdnRequest.ts:46`) and Home's bridge parser only JSON-parse bodies that look like JSON, so the height arrives as a string; `App.tsx:1832` discards non-numbers, so `currentBlockHeight` is **always null**. Downstream, `computeApprovalWindow` can never return `open`/`expired` and the approval dialog renders every window as "eligible now" — actively wrong for not-yet-open and expired windows — and the block ETA never displays. Predates the prior audit but was never flagged. Skeptic verified end-to-end incl. Core's `BlocksResource` and grepped for alternate paths: none. **Fix:** coerce in `getCurrentBlockHeight()` (`Number()` + `isFinite` guard) and add a test for a `text/plain` numeric body.

## 5. UI/UX (4 confirmed, 3 low)

**Health:** strong — skeletons, empty states, retention hint, jump-to-unread, persisted bookmarks/watermarks/sidebar, focus-trapped dialogs, bridge-gated affordances with tooltips; all prior UX items landed with no regression. Weaknesses cluster in error-state handling and the shared composer draft.

### 5.1 [Medium · new · CONFIRMED] Quiet background polls still clobber the UI with transient errors; pending-approvals wipes its data — `src/App.tsx:1852`
The 0b99681 fix covered only `loadMessages`/`loadActiveChats`. Five other loaders transition to `phase:'error'` in their catch regardless of `options.quiet`: `loadGroupMembers` (:1287), `loadAccountJoinRequests` (:1310), `loadAdminJoinRequests` (:1333), `loadMintingStatus` (:1353 — one-off quiet call, not timer), `loadPendingApprovals` (:1847). Join-request errors render as persistent banners over every chat; worse, `loadPendingApprovals` resets its value to empty, hiding the "Pending approvals (N)" button and emptying an open approval dialog on a blip. **Fix:** same quiet-guard pattern; never replace approvals data on a quiet failure.

### 5.2 [Medium · new · CONFIRMED] Failed chat load renders the previous chat's transcript under the new chat's header, no retry — `src/App.tsx:1504`
On a switch, a failed initial load keeps the prior chat's messages as the displayed value; `MessageList` is not gated on `messagesChatKey === selectedChatKey`, so chat A's transcript (possibly private) appears under chat B's title with only the error banner; recovery relies on background retries or re-selecting. Older-history has a Retry button; the main feed does not. **Fix:** gate the feed on the chat key and show error + Retry instead of a stale transcript.

### 5.3 [Medium · new · CONFIRMED] Composer draft — including armed edit drafts — carries across chat switches and can be sent to the wrong chat — `src/App.tsx:2124`
One global `draft`; `selectGroup`/`selectDirect` clear `composeContext` but not the draft. Worse, `startEdit` fills the draft with the old message's full text; switching chats silently drops the edit context, leaving historical (possibly private-DM) text armed as an ordinary message in the new chat — one Enter posts it. Skeptic confirmed no `setDraft('')` on any switch path. **Fix:** per-chat draft keying (like scroll bookmarks) or at minimum clear the draft when a switch discards an edit context.

### 5.4 [Medium · new · CONFIRMED] Modern dark muted/faint text below WCAG AA — `src/styles.css:518`
See §10.2 (same defect, reported by both dimensions; verified twice independently with exact contrast math). ## 7. Efficiency (5 confirmed after dedup, 2 low)

**Health:** the prior audit's data-layer fixes hold (decode/link caches, shared clock, reference-stable `mergeMessages`, content-visibility — Modern doesn't break it; memory growth well controlled). The gaps: one incompletely-landed prior fix and new debt from the post-audit sidebar-liveness and scroll-bookmark features.

### 7.1 [Medium · CONFIRMED · incompletely-applied prior fix] `React.memo` on MessageList/GroupList/DirectList is fully defeated — zero `useCallback` in App — `src/App.tsx:3584`
Prior-audit priority #2 was marked done via 7f1905f, but only the memo-wrap + shared clock landed; the explicitly recommended `useCallback`s never did. Every child gets fresh inline arrows / per-render function declarations plus an unmemoized `selectedTransactions` array, so the shallow compare fails on 100% of renders: each composer keystroke, WS frame, and quiet poll re-renders the entire feed, re-running per-row `renderMessageTextWithAppLinks` regex parsing. Skeptic downgraded high→medium (shared clock delivered most of the original win; `mergeMessages` bails on no-change frames; content-visibility caps paint) but confirmed every fact. *(Critic: status should read "incompletely-applied prior fix", not "new".)* **Fix:** `useCallback` the handler props + `useMemo(selectedTransactions)`; verify with a render count.

### 7.2 [Medium · new · CONFIRMED] N+1 polling sweep: 100-message fetch per listed group (and per direct) every 30s for a sidebar timestamp — `src/App.tsx:2686`
The post-audit sidebar-liveness effect fetches a full 100-message BASE64 window per group (up to 100 groups) every 30s — `getGroupMessages` has no `limit` override — solely to feed `mergeActivityTimestamp`, and re-reads groups already covered by the active-chats WebSocket. Mitigations exist (sequential, hidden-tab pause, local node) but it scales with the public group list. **Fix:** small `limit` option (5-10), skip WS-covered groups, refresh only on timestamp change.

### 7.3 [Medium · new · CONFIRMED] Unthrottled per-scroll-event localStorage JSON write + O(rows-above-viewport) rect walk — `src/MessageList.tsx:1317`
Every scroll event (frame-rate during flings) serializes the whole bookmark map and performs 3 synchronous localStorage ops (incl. a probe setItem/removeItem per call in `getStorage()`), plus `computeScrollPosition` walks `getBoundingClientRect` from the top of an unvirtualized list. From PR #25, post-audit. **Fix:** trailing debounce (250-500ms + flush on switch/unload), memoize the storage probe, bound the walk.

### 7.4 [Medium · new · CONFIRMED] `emoji-picker-react` statically bundled into the 1.0 MB chunk though it mounts on demand — `src/MessageList.tsx:11`
~300 KB (of 1,046 KB raw / 268 KB gz measured) parsed/executed on every start in mobile webviews, for a picker that renders only after React → '+'. **Fix:** `React.lazy(() => import('emoji-picker-react'))` behind the open flag; QDN serves the extra chunk from the same resource.

### 7.5 [Low · CONFIRMED, downgraded; known residual] Active-chats WS frames always allocate new state — `src/App.tsx:3087`
No no-change bailout (unlike `mergeMessages`), so each frame re-renders App + GroupList. Skeptic corrected scope: direct-side memos are *not* invalidated, and the prior audit already noted this residual (status: known, not new). **Fix:** shallow-compare groups in the updater and return `current` when unchanged.
