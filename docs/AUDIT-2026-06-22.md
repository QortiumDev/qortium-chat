# Qortium Chat — Comprehensive Multidimensional Audit

**Date:** 2026-06-22 · **App:** `qortium-chat` @ `main` (0a8d790) · **Live node:** Previewnet Core `v1.1.2`, 99% synced

## Method

Multi-agent audit. A Claude workflow ran 7 dimensions in parallel (28 agents), with **every code-level finding adversarially verified** by an independent skeptic agent; an 8th dimension (efficiency/UX) was re-run after a failure. Live public-chat (210 msgs) and QDN Help-app (8 `qhelp*` docs) feedback were analyzed separately.

Verification rejected 3 candidate findings as false positives (listed at the end) and downgraded several. What follows is the surviving, evidence-backed set.

The highest-value work is **performance + platform-modernization + i18n backfill**, plus a cluster of **accessibility** fixes for screen-reader users. Three real-user requests from live feedback converge with the audit.

## 3. i18n parity — Medium

- **Missing 3 languages: `el` (Greek), `hi` (Hindi), `nb` (Norwegian Bokmål).** Home (`src/displaySettings.ts` `LANGUAGE_OPTIONS`, 23) and Core (`src/main/resources/i18n`, 23) both ship them; this app's `SUPPORTED_LANGUAGES` (`i18n.ts:24-45`) has 20. When Home reports one, `normalizeLanguage()` returns null and **the whole UI silently falls back to English.**
  → Add the three locale files + register in `i18n.ts`/`SUPPORTED_LANGUAGES`. Even English-seeded stubs fix `document.dir`/`lang` and honor the picker.
- **All 19 non-en locales are missing the same 19 keys** (258/277 each) — a feature batch (unread indicators, @mentions, direct-chat removal, retry, older-message loading, name-lookup errors) was added to `en.ts` and never propagated. Degrades gracefully to English (no crashes, by design: `catalog[key] ?? EN_STRINGS[key]`), but users see English islands.
  → Backfill, and **add a Vitest guard** that fails when any locale's keyset diverges from `en.ts`.
- **RTL (`ar`,`he`) is correctly implemented** — `dir`/`lang` set, `[dir='rtl']` rules present.

## 4. Efficiency & platform best-use

> Note: `App.tsx` is **5,509 lines**, not the "~1300" in `CLAUDE.md` — that figure is badly stale (doc fix recommended).

- **High — Per-address fan-out for names+avatars; `RESOLVE_IDENTITIES` unused.** `useAvatarProfiles` loops `loadAvatarProfile` per address (`App.tsx:1078-1100`), each doing `GET_ACCOUNT_NAMES` + `GET_QDN_RESOURCE_PROPERTIES` + `FETCH_QDN_RESOURCE` (`avatarProfiles.ts:130-157`). A busy group with 100 senders → **100+ bridge round-trips.**
  → Add `resolveIdentities(addresses, actions)` in `coreApi.ts` gated on `hasBridgeAction(...,'RESOLVE_IDENTITIES')`, chunk at 500; keep the hardened image fetch (size-check + MIME allowlist + `blob:`) for the actual image rather than binding the returned URL straight into `<img src>`; fall back to per-address only when the action is absent.
- **High — No component memoization; whole tree re-renders on a 30s clock and every WS frame.** Zero `React.memo` in the codebase; `GroupList`/`DirectList`/`MessageList` each run their own `setInterval(setNow,30000)` (`App.tsx:1186,1297,2072`); active-chats WS calls setstate every frame (`App.tsx:4824-4879`).
  → `memo` the list components + message row; **one shared "now" clock**; `useCallback` for child callbacks.
- **Medium — Message feed not virtualized + re-decodes every message each render.** `combinedMessages` grows unbounded (`mergeMessages(...,Infinity)`); the map calls `decodeChatMessage`/`getImageQdnResources`/`getMediaQdnResources` per render (`App.tsx:2212-2224`) with no decode cache.
  → Cache decoded results (`WeakMap<ChatMessage,Decoded>` in `chatText`) and window the list once paged history is large.
- **Medium — Over-eager refetch after writes.** Direct send/reactions call full `loadAccountData` (member groups + active chats + join requests + admin + minting) then `loadMessages` (`App.tsx:3926-3930, 3964-3968`) → flicker.
  → After a direct send, refresh only active-chats/messages.
- **Low** — `mergeMessages` rebuilds a full `Map` + re-sort every WS frame (`App.tsx:363-383`) → fast-path append-and-sort-tail for small deltas. · Approval tally pulls latest 100 `GROUP_APPROVAL` txs network-wide and filters client-side (`coreApi.ts:320-337`) → can undercount on a busy chain; raise/page the limit. · `getMintingStatus` REST fallback makes 3 sequential calls (`coreApi.ts:373-391`) → `Promise.all` the last two.
- **Info — Platform coverage is strong**: reactions, edits/replies via `chatReference`, QDN image previews + media player, minting, full on-chain `GROUP_APPROVAL` voting are all genuinely wired. The one gap is **no attach/publish-on-send** path (renders inbound QDN media but can't attach outbound).

## 6. Accessibility — screen readers & keyboard

- **High — Live feed isn't a live region.** `<ol className="message-list">` has no `aria-live`/`role="log"` (`App.tsx:2172`); WS-arriving messages are **silent to SR users not actively in the list**.
  → Wrap transcript (or a visually-hidden mirror of just-arrived messages) in `role="log" aria-live="polite" aria-relevant="additions"`.
- **Medium — Dialogs declare `aria-modal` but don't behave modally.** `AccountInfoDialog`/`GroupApprovalDialog`/`AvatarLightbox` only attach Escape — no initial focus, no Tab-trap, no focus restore, background not inert (`App.tsx:609-637, 782-792, 1023-1033`). Tab walks behind the overlay.
  → Mirror the members-drawer pattern (focus in, trap, restore, `inert` background).
- **Medium — `outline:none` on `:focus-visible` with hover-identical replacements.** Group/direct rows + inline message controls lose a distinct keyboard focus indicator (`styles.css:894-903, 861-864`) — WCAG 2.4.7.
  → Add a hover-distinct focus ring (`box-shadow`/real `outline`).
- **Medium — Low-contrast meta text.** `--qc-color-text-faint #89918e` on `#fff` ≈ 2.9:1 (timestamps); dark equivalent ≈ 4.0:1 — both below AA 4.5:1 (`styles.css:67,52,1574`).
  → Darken/lighten until ≥4.5:1.
- **Low** — `role="toolbar"` quick-reaction row lacks an accessible name (`App.tsx:1475`). · Member roster & lists are `div`/`span` not `ul`/`li` (`App.tsx:2485,1197,1308`) — operable but not announced as lists.

## 7. Responsiveness / mobile — mostly strong

Genuinely well-engineered: correct viewport meta (`index.html:5`), `body min-width:320px`, two breakpoints (860px collapses 2/3-pane grid to single-view nav + off-canvas members drawer; 600px stacks topbar/composer), pervasive `minmax()/min()/clamp()` + `min-width:0`, `dvh` + `env(safe-area-inset-*)`, JS-clamped reaction popover. Remaining nits (all **Low**):

- Breakpoints are width-only and ignore the large **text-scale** (up to 2.1×) → layout can crowd under "huge" text (`styles.css:384-406, 2485`). Consider `@container` queries.
- EmojiPicker fixed `height={360}` can exceed short/landscape viewports (`App.tsx:1508-1520`) → make viewport-relative.
- Several touch targets < ~44px (icon-button 34px, direct-row remove 26px, reaction-close 24px) (`styles.css:801-808, 994-996, 1793-1796`) → enlarge under `@media (pointer:coarse)`.
- Add `viewport-fit=cover` to fully activate the safe-area padding already in CSS.

## 8. Correctness — 1 real bug (no blockers)

- **Medium — Quiet poll / WS-fallback errors clobber a working chat.** `loadMessages` catch always sets `{phase:'error', value: messages.value}`; the `!options.quiet` guard only skips clearing the chat key, **not** the error transition (`App.tsx:3420-3429`). The 15s direct/closed-group poll (`:4726`) and WS REST-fallback (`:4793`) therefore flash an error banner + stale closure value over a live chat on any transient blip.
  → In the catch, skip the error transition entirely when `options.quiet` (keep last-good `ready`), or use a functional update so the displayed value is never replaced. *(Also addresses the Help-app guidance to distinguish "waiting on chain" from real errors.)*
- **Low — Strict `before` paging can drop same-timestamp boundary messages.** `before: oldest.timestamp` is exclusive (`App.tsx:3461-3474`, `coreApi.ts:146-150,558`); messages in the same millisecond on the boundary are never returned.
  → Page with `oldest.timestamp + 1` and rely on existing signature dedupe in `mergeMessages`.
